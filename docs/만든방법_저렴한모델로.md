# 이 도구는 어떻게 만들었나 — 그리고 비싼 모델 없이 만드는 법

이 도구의 코드는 전부 **Claude Code(데스크탑 앱 코드 탭)** 에서 한국말로 시켜서 나왔습니다. 사람이 친 코드는 없습니다. 만들 때는 최상위 모델(Fable)을 썼지만, 같은 결과를 **Opus·Sonnet처럼 더 싼 모델로도** 낼 수 있게 이 리포 자체가 그 순서대로 구성돼 있습니다. 비싼 모델은 "무엇을 만들지"를 정할 때만 잠깐 쓰고, 코드는 싼 모델이 씁니다.

## 핵심 원리 한 줄

**설계서를 먼저 받고, 코드는 작게 쪼개서 시킨다.** 비싼 모델이 잘하는 건 큰 그림이고, 싼 모델도 잘하는 건 "명확한 한 조각"입니다. 그래서 설계서 한 장이 있으면 나머지는 싼 모델로 충분합니다.

## 4단계

| 단계 | 시키는 말 | 모델 | 결과물 |
|---|---|---|---|
| 1. 설계서 | "영업사원 1인용 고객관리 도구를 만들 거야. 구글 시트가 DB, Apps Script 웹앱, 카카오 알림. 시트 탭·컬럼·알림 규칙·화면을 설계서로 먼저 써줘. 코드는 아직 쓰지 마." | **Opus** (한 번만) | [`spec.md`](spec.md) 같은 문서 |
| 2. 계산만 하는 부분 | "설계서의 알림 규칙 4가지 조건유형을 순수 함수로 만들어줘. 스프레드시트 API는 쓰지 말고, Node에서 테스트할 수 있게." | **Sonnet** | `src/Rules.gs` `src/Dashboard.gs` `src/DemoData.gs` |
| 3. 테스트 | "위 함수들의 경계 케이스(D-0, D-7, D-8, 2월 29일) 테스트를 써줘. 실패하면 고쳐." | **Sonnet** | `dev/run-tests.js` (13개) |
| 4. 시트·화면 연결 | "설계서 3장 스키마대로 시트를 읽고 쓰는 부분, 그리고 대시보드 화면 하나만 먼저." → 화면 하나씩 추가 | **Sonnet** (막히면 그 조각만 Opus) | `src/SheetRepo.gs` `src/View*.html` |

포인트는 2단계입니다. 규칙 계산을 스프레드시트와 떼어놓으면 **테스트가 돌아가고**, 테스트가 있으면 싼 모델이 틀려도 바로 잡힙니다. 이 리포의 `dev/run-tests.js`가 그 역할입니다.

## 싼 모델로 시킬 때의 습관 5개

1. **계획 모드 먼저.** 바로 실행하지 말고 "어떻게 할 건지 계획부터"를 받아 읽고 수락합니다. 싼 모델의 실수 대부분이 여기서 걸립니다.
2. **한 번에 화면 하나.** "대시보드·고객·입력·설정 다 만들어줘"는 비싼 모델도 흔들립니다. 화면 하나 → 확인 → 다음 화면.
3. **설계서를 항상 같이 줍니다.** "spec.md 3장 스키마 기준으로"처럼 근거 문서를 지목하면 싼 모델이 지어내는 게 줄어듭니다.
4. **테스트를 먼저 통과시키고 화면을 붙입니다.** 화면부터 만들면 어디서 틀렸는지 못 찾습니다.
5. **막히는 조각만 비싼 모델로.** 카카오 OAuth 토큰 갱신처럼 한 번 꼬이면 오래 잡는 부분만 Opus로 올리고, 풀리면 다시 내립니다. 모델은 데스크탑 앱에서 대화 중에 바꿀 수 있습니다.

## 사용량이 새는 곳 두 군데

- **폴더를 통째로 읽힐 때.** "이 폴더 다 보고 고쳐줘" 대신 "`src/Rules.gs`만 보고". 이 리포는 파일이 역할별로 나뉘어 있어 하나만 지목하면 됩니다.
- **틀려서 다시 시킬 때.** 한 번 맞은 지시문은 저장해 두고 다음에 그대로 씁니다(스킬). `skills/sales-weekly-picks`가 그 예입니다.

## 이 리포로 직접 해보기

1. `docs/spec.md`를 열어 둡니다.
2. Claude Code 코드 탭에서 모델을 Sonnet으로 두고: *"spec.md 4장 알림 규칙을 순수 함수로 다시 구현해줘. 기존 `src/Rules.gs`는 보지 말고. 끝나면 `node dev/run-tests.js`로 확인해."*
3. 13개 테스트가 통과하면, 싼 모델로도 이 도구의 핵심이 그대로 나온다는 걸 직접 확인한 겁니다.

## 실측 (2026-09-17)

위 "직접 해보기"를 그대로 돌려봤습니다. 기존 `src/Rules.gs`를 지운 사본에서 **Claude Sonnet**에게 `docs/spec.md`·`src/Config.gs`·`src/Test.gs`와 다른 파일의 호출부만 보고 Rules.gs를 다시 쓰게 했습니다.

- 결과: **13/13 테스트 통과, 첫 시도에서.** 반복 수정 0회.
- Sonnet이 스스로 푼 지점: ① 테스트에 안 드러난 함수 시그니처를 다른 파일의 호출부에서 역산 ② "같은 고객·같은 규칙은 가장 급한 1건"의 "급한"이 조건유형마다 반대 방향(경과일은 클수록, D-일은 작을수록)이라는 걸 정렬 테스트로 역추적 ③ 200자 청크 형식은 테스트가 불변조건만 검증해 자유 설계.
- 산출물: [`Rules.sonnet-reimpl.gs.txt`](Rules.sonnet-reimpl.gs.txt) (319줄, 원본 304줄). 원본과 함수 구성은 거의 같고 이름만 일부 다릅니다.

즉 설계서와 테스트가 있으면 규칙 엔진 같은 핵심 로직은 싼 모델로 충분하다는 게 이 리포에서 실제로 재현됐습니다.
